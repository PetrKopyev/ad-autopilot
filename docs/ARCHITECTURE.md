# Архитектура

## Компоненты

```
                  браузер владельца
                         │ HTTPS
                  ┌──────▼──────┐
                  │    Caddy    │  сертификат, защитные заголовки,
                  │  :80 / :443 │  статика интерфейса (frontend/dist)
                  └──────┬──────┘
                         │ /api/*
                  ┌──────▼──────┐          ┌──────────────┐
                  │     api     │◄────────►│  PostgreSQL  │
                  │   FastAPI   │          │      16      │
                  └─────────────┘          └──────▲───────┘
                                                  │
                  ┌─────────────┐                 │
                  │   worker    │◄────────────────┘
                  │ планировщик │
                  └──────┬──────┘
                         │ прямые API
        ┌────────────────┼──────────────────┬───────────────┐
        ▼                ▼                  ▼               ▼
   Яндекс Директ     VK Реклама      Яндекс Метрика   YandexGPT / YandexART
```

- Caddy (`deploy/Caddyfile`) отдаёт интерфейс из `frontend/dist`, `/api/*` проксирует в `api`, добавляет HSTS, CSP и другие защитные заголовки.
- `api` (`backend/app/main.py`, `backend/app/api/`) обслуживает экраны: вход через Яндекс ID, подключение кабинетов, мастер запуска, статистику, историю, откат, настройки. Состояние хранится в PostgreSQL; сессия живёт в cookie `__Host-session`, защита от CSRF через `__Host-csrf` и заголовок `X-CSRF-Token`.
- Картинки и ролики лежат в томе `media` (`/data/media/<business_id>/`), общем для `api` и `worker`.
- Отключение кабинета и удаление данных: сначала остановка рекламы на затронутых площадках (до минуты, при любом `DRY_RUN`), затем удаление и отзыв токенов. Если площадка остановку не подтвердила, ответ сообщает об этом ([PRIVACY.md](PRIVACY.md)).
- `worker` (`backend/app/worker/main.py`) тот же образ с другой командой. Раз в минуту пишет «пульс», раз в 30 минут запускает все шаги, которые на этот момент подошли по расписанию (раздел «Расписание»). Миграции выполняет отдельный сервис `migrate` до старта `api` и `worker`.
- Ключи и адреса приходят из переменных окружения (`backend/app/config.py`, [DEPLOY.md](DEPLOY.md)): для своих приложений Яндекса и VK код менять не нужно.
- В демо-режиме (`PLATFORM_MODE=fake`) планировщик работает внутри процесса `api`, а контейнер `worker` просто ждёт; площадки заменены симулятором.

## Где решает код, а где нейросеть

| Нейросеть (YandexGPT, YandexART) | Код (чистые функции без сети, `backend/app/domain/`) |
|---|---|
| Черновик описания бизнеса по тексту сайта (каждое поле с цитатой) | Проверка цитат по тексту страницы, непрошедшее превращается в вопрос владельцу |
| Тексты объявлений | Проверка текстов: лимиты символов, стоп-слова, числа и контакты только из утверждённого описания, медицинский дисклеймер; до двух перегенераций, затем шаблон |
| Идеи картинок | Итоговый запрос к YandexART, ограничения, лимиты трат |
| | Все решения: остановить, повысить бюджет, запустить A/B-тест, вердикт теста, разбивка бюджета, страж расхода |

Нейросеть не принимает ни одного решения о рекламе. Правила: [RULES.md](RULES.md).

## Адаптеры площадок

Единый интерфейс `AdPlatform` (`backend/app/platforms/base.py`): создание дерева кампании, единственная точка записи `apply(Operation)`, чтение состояния для сверки, статистика, расход за сегодня, модерация, загрузка картинок, маркировка, лимиты.

- `DirectAdapter` (`direct.py`): Директ API v5 и v501 (единая перфоманс-кампания). Песочница — тот же адаптер с хостом `api-sandbox.direct.yandex.com` (`DIRECT_SANDBOX=true`).
- `VkAdapter` (`vk.py`): VK Реклама API v2.
- `FakeAdapter` (`fake.py`): симулятор для тестов и демо. Виртуальные часы, заданные «истинные» показатели объявлений, конверсии с задержкой, модерация с отказами, сбои площадки (429, 5xx, истёкший токен) и режим «злой площадки», которая тратит больше лимита, чтобы проверять страж.
- `MetricaClient` (`metrica.py`): счётчики и цели Метрики; в демо подставляется заглушка.
- Прогноз обращений до запуска (`direct_forecast.py`, `backend/app/services/forecast.py`): прогноз бюджета Директа (API v4 Live) и доля обращений по Метрике; правила — в [RULES.md](RULES.md).
- `AdapterRegistry` (`backend/app/services/registry.py`) выбирает адаптер по паре (бизнес, площадка) и пересобирает его при смене данных кабинета.

## Поток изменения

Любая запись в кабинет проходит одним путём (`backend/app/services/changes.py`):

1. В `change_log` создаётся запись со статусом `pending`: актёр (автопилот, владелец, система, внешнее изменение), операции с `before` и `after`, причина и цифры, на которых принято решение.
2. Адаптер применяет операцию на площадке.
3. Сервис перечитывает состояние площадки и сверяет с ожидаемым. Исходов четыре. Совпало: `applied`. Не совпало: `failed` с описанием расхождений. Площадка недоступна для чтения: запись остаётся `pending`. Площадка ещё проверяет объявления (статусы «на проверке», «черновик»): запись сразу `applied`, в `evidence._service.review` лежат сущности, которые она проверяет, а кампания получает отметку ожидания (см. ниже).
4. При старте воркер доводит все `pending`: сверяет фактическое состояние и решает «применено или нет». Пока у бизнеса на площадке есть непросверенное изменение, новые изменения на ней не делаются (защитная остановка проходит всегда).

При `DRY_RUN=true` шаги 2 и 3 пропускаются только для решений автопилота (`actor=autopilot`): они записываются в историю как «предложено», в кабинеты не уходят, доли бюджета площадок по цене обращения не меняются. Действия владельца, откат, пересчёт лимитов от остатка бюджета, продление даты окончания кампании Директа и остановка стражем бюджета применяются при любом `DRY_RUN`: иначе кампания закончилась бы в конце недели, а перерасход не остановился бы.

### Ожидание проверки объявлений площадкой

Ожидание модерации — состояние кампании (`campaigns.review_since`), а не зависшая запись журнала: локальный статус остаётся нашей целью («работает»), включение, упёршееся в проверку, пишется как `applied` с `_service.review` и не блокирует новые изменения. Цель доводит шаг `sync.settle_review` (раз в час): включает одобренное, но выключенное, отправляет на проверку черновики (запись `MODERATION_SETTLE`), доводит паузу, не применённую к черновику. Через 5 дней проверки владелец получает уведомление `MODERATION_LONG`; если отклонены все объявления кампании, ожидание снимается (`MODERATION_ALL_REJECTED`). Остановленную владельцем кампанию `settle_review` не включает.

«Продолжить» идемпотентно: не включённые площадкой кампании остаются со своей паузой, повторное нажатие включает оставшиеся. Кампания, удалённая в кабинете, не ломает шаги: одно уведомление `CAMPAIGN_NOT_FOUND`, id запоминается в `missing_campaigns`.

Откат: это новая запись `kind=revert` с обратными операциями, старая получает `reverted`; история не переписывается. Перед откатом читается текущее значение: если оно не совпадает с тем, что поставил сервис (кто-то поменял в кабинете), владельцу показывается предупреждение и откат идёт только по подтверждению. Созданное объявление через API не удалить, поэтому его откат это пауза и архив. После отката владельцем объект получает `frozen_until` на 14 дней: автопилот не повторяет то же действие. Изменения, обнаруженные в кабинете и сделанные не сервисом, записываются как `actor=external`. Автопилот никогда ничего не удаляет, только ставит на паузу.

## Четыре слоя защиты бюджета

Площадки не гарантируют жёсткий дневной предел, а отчёты о расходе приходят с задержкой, поэтому «ни разу не превысить» обеспечивают четыре слоя (`backend/app/domain/budget.py`, `backend/app/services/budget_guard.py`):

1. Резерв. Размещается не весь месячный бюджет, а `бюджет × (1 − резерв)`; резерв 8% на НДС, перерасход и задержку отчётов. Остаток не выделяется никогда.
2. Лимиты на стороне площадки, которые работают даже при остановке воркера: в Директе недельный лимит стратегии `WeeklySpendLimit`, в VK дневной лимит плана `budget_limit_day` (общий `budget_limit` API не принимает вместе с дневным). Сервис ставит лимит в 1/1,25 от разрешённого, на случай, что площадка превысит его на 25%. Сумма лимитов по кампаниям не выше разрешённого остатка, лимиты пересчитываются ежедневно и никогда не растут выше остатка.
3. Страж каждые 30 минут: читает расход за месяц, и если `расход ≥ бюджет − запас`, ставит на паузу все кампании и пишет в историю. Запас равен максимуму, который можно потратить за два пропущенных опроса: `суммарный дневной лимит × 1,5 × 30 × 2 / 1440`.
4. Сверка при каждом запуске воркера: если площадка сообщает расход больше допустимого, это тревога: пауза всех кампаний и запись в историю (`SPEND_MISMATCH`).

Расход «потрачено» — большее из двух значений на площадке: снимка стража (`budget_ledger`) и суммы по отчётам (отдельно в статистике — `reported_kop`). Траты на нейросети считаются отдельно и ограничены (`AI_SPEND_*_LIMIT_RUB`).

Дневной лимит считается как остаток разрешённого бюджета, делённый на оставшиеся дни, но не больше 1,3 среднего дня. Исключение — поднятие темпа до недельного минимума Директа (ниже): дневной лимит этой недели поднимается до минимума и в последний день недели может доходить до 366 ₽ в день при любом среднем дне. Первый месяц считается пропорционально дням после запуска. Между площадками бюджет делится 70/30 (Директ/VK), если подключены обе, иначе всё уходит на одну; раз в 14 дней доли сдвигаются к более дешёвой по цене обращения не более чем на 10 процентных пунктов. Недельный минимум Директа добирается темпом, а не паузой, пока остаток месяца его покрывает, а доля площадки, вся ушедшая в минимум, временно переходит работающей площадке ([RULES.md](RULES.md)).

## Расписание воркера

`backend/app/worker/main.py`, `backend/app/worker/jobs.py`. Шаги идемпотентны: у каждого есть ключ слота, один слот выполняется один раз, перезапуск безопасен. На бизнес берётся блокировка PostgreSQL (`pg_try_advisory_lock`), параллельно два шага одного бизнеса не идут. Время слотов московское.

Блокировка берётся без ожидания из отдельного пула соединений (`backend/app/db/session.py`): пул занят — пользователь получает 503 «сервер занят», этот бизнес уже обрабатывается шагом воркера или перемоткой демо — 409. Действия владельца, которым нужна блокировка (остановка, отключение кабинета, проверка сайта, шаги мастера), ждут её до 15 секунд и только потом отвечают 409.

Устойчивость шагов:

- Запуск рекламы держит блокировку бизнеса до перехода в `running`; устаревший план и второй одновременный запуск отклоняются. Брошенный запуск восстанавливается повторным нажатием «Запустить» (неподтверждённое сверяется с площадкой), иначе воркер останавливает созданное и отправляет уведомление.
- Кампании прежних планов не получают бюджет и не включаются в новом месяце и откатом; остановка и учёт трат их видят.
- Закрытый, удалённый или с нечитаемым токеном кабинет одной площадки не мешает стражу и шагам другой.
- Токены продлеваются фоновым шагом: VK (живёт около суток) и Яндекс Директ (по refresh-токену за 30 дней до истечения). Если продление не удалось и до конца токена меньше 7 дней, владелец получает уведомление «Переподключите Директ».
- Опрос модерации сохраняет результат по каждой кампании отдельно. Уведомления могут иметь срок и после него не показываются.
- Перемотка демо гоняет шаги только своего бизнеса и не пишет «пульс».
- Доступ к базе из `api` синхронный осознанно ([LIMITATIONS.md](LIMITATIONS.md)).

| Шаг | Когда | Что делает |
|---|---|---|
| `heartbeat` | каждую минуту | запись «воркер жив» в `worker_runs`; хранится сутки |
| `prune` | ежедневно в 04:10 | уборка: пульс старше суток и «из будущего», прогоны шагов старше 90 дней, просроченные сессии и запросы входа; уведомления не удаляются |
| `month_rollover` | при каждом тике | в начале месяца новый бюджет и возобновление; если продление выключено, реклама останавливается (`MONTH_STOP`); за три дня до конца месяца владельцу приходит напоминание |
| `budget_guard` | каждые 30 минут | расход, страж, сверка; остаток на счёте площадки: меньше дневного лимита её кампаний — уведомление `BALANCE_LOW`, одно до пополнения |
| `sync_moderation` | раз в час | статусы и причины отказов модерации; объявление, отклонённое за текст, заголовок или опечатку (не за медицину, документы, лицензию), один раз переписывается ИИ тем же заходом и поводом, проверяется и отправляется на модерацию заново (`REJECTED_REWRITE`); не вышло — остаётся уведомление владельцу |
| `sync_stats` | раз в 3 часа | загрузка статистики, последние 7 дней перезаписываются (конверсии «доезжают»), устоявшимися считаются дни до «сегодня − 2» |
| `optimize` | ежедневно с 06:00 | снимок, решения по правилам, применение с предохранителями |
| `experiments_tick` | ежедневно с 06:00 | старт новых A/B-тестов, вердикты |
| `rebalance_budget` | ежедневно с 06:00 | пересчёт лимитов и долей площадок |
| `clients_survey` | по понедельникам с 10:00 | вопрос владельцу «сколько обращений стало клиентами» |

После простоя выполняется текущий слот каждого шага; пропущенные слоты не догоняются. При старте воркер отдельно доводит `pending` и сверяет расход со стражем (слой 4).

## Данные

PostgreSQL, миграции alembic (`backend/alembic/`). Деньги хранятся целыми копейками. Токены кабинетов, ИНН и телефон шифруются Fernet-ключом из `TOKEN_ENCRYPTION_KEY` на уровне колонок. Идентификаторы сессий хранятся хешем. Основные таблицы: `users`, `businesses`, `platform_accounts`, `plans`, `campaigns`, `ad_groups`, `ads`, `targets`, `stats_daily`, `budget_ledger`, `change_log`, `experiments`, `leads_survey`, `worker_runs`, `llm_calls`, `art_calls`.

Статистика хранится по дням и объявлениям; расход считается как его списывает площадка (с НДС). Для решений используются только устоявшиеся дни, для стража и сверки данные «до сейчас».

### Миграции

Миграции выполняет сервис `migrate` (`alembic upgrade head`) до старта `api` и `worker`; воркер на время миграции останавливают. В `alembic/env.py` задан `lock_timeout = 5s`: занятая таблица приводит к повтору миграции, а не к зависанию API. Для таблиц с данными (с `0004`): индексы и уникальность — `CONCURRENTLY`, `CHECK` и внешние ключи — `NOT VALID` с отдельным `VALIDATE`, новые столбцы допускают `NULL` или имеют постоянный `DEFAULT`, схема совместима с кодом предыдущего релиза, у каждой миграции есть `downgrade` (потери описаны в её docstring). Тест `tests/db/test_migrations.py` проходит `upgrade head` → сравнение с моделями → `downgrade base` → `upgrade head`.
